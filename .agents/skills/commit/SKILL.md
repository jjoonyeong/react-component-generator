# Commit

## 1. 변경사항 분석

- 저장소의 적용 가능한 지침을 확인한다.
- `git status --short`, `git diff`, `git diff --cached`로 미스테이징·스테이징 변경을 모두 확인한다. 추적되지 않은 파일은 내용을 별도로 검토한다.
- 저장소가 아니면 자동으로 초기화하지 말고, 기존 저장소 경로 또는 새 저장소 초기화 여부를 사용자에게 확인한다.
- 변경사항이 없으면 커밋하지 않고 알린다.
- 비밀정보, `.env`, 의존성 디렉터리, 빌드 산출물이 커밋 대상에 포함되지 않는지 확인한다.

## 2. 논리적 단위로 분류

- 기능 추가, 버그 수정, 구조 개선, 유지보수 등 변경 목적에 따라 나눈다. 하나의 동작을 완성하는 코드와 관련 테스트는 함께 묶는다.
- 기존 스테이징 상태를 존중하고, 요청 범위를 벗어난 변경을 임의로 포함하거나 되돌리지 않는다.
- 파일 안에 서로 다른 목적의 변경이 섞이면 필요한 경우 부분 스테이징을 사용한다.
- 변경에 맞는 검증을 실행하고 결과를 확인한다. 검증이 실패하면 원인을 해결하거나, 해결에 사용자 판단이 필요한 경우 실패 내용을 알리고 중단한다. 미실행 검증은 완료 보고에 명시한다.

## 3. 한국어 커밋 메시지 작성

형식: `<type>: <한국어 요약>`

| type | 용도 |
| --- | --- |
| feat | 기능 추가 |
| fix | 버그 수정 |
| refactor | 기능을 유지하는 구조 개선 |
| chore | 설정, 도구, 문서 등 유지보수 |

- 요약은 실제 변경 결과를 구체적으로 표현한다. 예: `fix: 빈 프롬프트의 생성 요청 방지`.
- 여러 커밋이 필요하면 각 커밋의 메시지와 포함할 변경을 제시한다.

## 4. 추가 승인 없이 커밋

- 사용자의 커밋 요청을 해당 범위의 커밋 실행 권한으로 간주한다. 변경 범위와 메시지를 간단히 알리고 추가 승인 질문 없이 커밋까지 진행한다. 사용자가 명시적으로 검토나 승인 대기를 요청했다면 그 지시를 따른다.
- “모든 변경사항” 요청이면 추적되지 않은 파일까지 검토하여 포함한다. 특정 변경만 요청했다면 그 범위를 유지한다.
- 대상 파일 또는 변경 부분만 스테이징하고 `git diff --cached`와 `git diff --cached --check`로 실제 커밋 내용을 확인한다.
- Git 작성자 정보가 없으면 이름과 이메일을 요청한다. 임의로 만들거나 전역 Git 설정을 변경하지 않는다.
- 작성한 메시지로 커밋한다. 훅이나 서명 검증이 실패하면 우회하지 말고 원인을 보고한다.
- 완료 후 커밋 해시, 메시지, 남아 있는 변경사항을 알린다. 푸시와 기존 커밋 수정은 별도 요청 없이 실행하지 않는다.
